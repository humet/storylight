## One-image-per-stage image workflows (2026-07-20)

**Root cause fixed (found live in production):** the engine runs exactly ONE stage per Vercel Workflow (WDK) step = one serverless invocation (`src/adapters/jobs/wdk-workflow.ts` `runOneStage` is a `"use step"` calling `engine.runNextStage`). A stage that made MANY sequential real image calls exceeded the function max-duration, so WDK timed out and REPLAYED the WHOLE stage — re-spending on every real image API call and never completing (confirmed: real gateway image spend, no finished result). Fix: **one real image call per engine stage**, each stage short + idempotent.

**LIVE-VERIFIED in production (2026-07-20, deploy `d47db01`):** full real chain works end-to-end. M4 reference generation advanced view-by-view (`paint-front-portrait` → … → `record-candidate-set`) to `completed`, producing 6 real Gemini reference images (~1.0–1.4 MB each, not the tiny fake medallion), approved via the appearance UI. A one-off story with that character then generated real chapter scenes: text published first, 5 `generate-illustration` child workflows ran as per-phase steps (observed `waiting` between phases — the yield that proves per-step execution), all real Gemini calls, **bounded** (per-spec ≤3-image cap held; no timeout/replay/runaway). 2 of 5 scenes were vision-approved and render in the reader (real 896px/1200px images conditioned on the character references); the other 3 hit manual-review and correctly show the text-first fallback (never a wrong-identity image, rule 7). No active WDK runs remain after (0 spending).

**Follow-ups:**

- **Illustration approval rate is low (2/5 in the live test)** — vision review rejects scenes whose identity/continuity it isn't confident in. This is correct _safety_ behaviour (better no image than a wrong-child image), but it's a QUALITY/tuning matter: improve reference-conditioning fidelity (prompt, which/how many reference views are fed) and/or calibrate vision-review strictness.
- **Vision-review robustness hardened (2026-07-20):** `gateway-vision-model` no longer uses the SDK's strict `Output.object`; it asks for compact JSON in plain text and parses via the pure, unit-tested `parseVisionVerdict` (tolerates code fences / surrounding prose / string-braces), retrying up to 3× and only failing SAFE (never fabricating a verdict, never silently passing). **HONEST caveat on the premise:** the first probe showed `Output.object` returning `NoObjectGeneratedError` 4/4, but a second cheap probe on the SAME saved scenes showed `Output.object` succeeding 4/4 — so its failure is INTERMITTENT, not consistent, and I do NOT have clean evidence it was the main driver of the 2/5 approval rate. What IS verified: the new lenient prompt+parse recovers a valid verdict on real model output, and retry+fail-safe strictly removes the intermittent hard-fail path (a rejection that had nothing to do with image quality). So this is a genuine robustness improvement but its impact on the approval rate is UNMEASURED — needs one live re-test. The remaining rejections may be genuine identity/quality calls (the real tuning work). (A `try Output.object → fall back to lenient` belt-and-suspenders variant is an option if this ever regresses.)
- **Seedream 5.0 probe (2026-07-20):** on one clean test case, `bytedance/seedream-5.0-pro` matched Gemini on identity (98%) + style at **~3–4× lower cost** ($0.035/image flat vs gemini-3.1-flash-image $0.101 @2K / gemini-3-pro-image $0.134). Accessed via the dedicated image API (`generateImage` with `prompt:{images,text}`) — reference conditioning confirmed working. A candidate for the routine tier pending the proper `pnpm eval` set (multi-child / varied scenes), not one probe.
- **Multi-set M4:** `setCount` forced to 1 (one candidate set). Multiple candidate sets → fan-out to per-set child workflows (each still one-image-per-stage) is the follow-up.
- **Stale workflow rows:** ~37 orphaned `running`/`queued` `workflow_executions` rows accumulated across this session's live testing (mostly `generate-illustration` child jobs created before the child-dispatch fix). They are INERT — no active WDK driver, zero spend — but the status column is never reconciled to terminal when a WDK run is cancelled/orphaned. Consider a reconciliation sweep (mark rows terminal when their WDK run is gone) or just clear test data on this personal project.

**M4 `generate-character-candidates`** (`src/application/workflows/generate-character-candidates-workflow.ts`) — the main offender (its single `paint-candidates` stage looped `setCount × 6` real image calls). Now **one stage per reference view + a final assembly stage** (7 stages):

- Stage keys: `paint-front-portrait`, `paint-three-quarter`, `paint-full-body-front`, `paint-side-view`, `paint-expression`, `paint-default-outfit`, then `record-candidate-set`. (Derived from `REFERENCE_VIEWS`; keys are `paint-${view}`.)
- Each `paint-<view>` stage generates + validates + uploads EXACTLY ONE quarantined reference image (bytes to private storage), then persists that view's asset metadata as its stage output (IDs/metadata only — never bytes). The final `record-candidate-set` stage reads the six persisted view assets and records the `candidate_set` row atomically. The appearance UI's read model (`listPendingCandidateSets`) is unchanged and shows the set once the final stage completes.
- **`setCount` forced to ONE set** (`SET_INDEX = 0`; the legacy `setCount` input field is still accepted but ignored). A multi-set fan-out would multiply the per-run call count again (`setCount × 6`) — it is a documented **FOLLOW-UP**, not done here.
- Service split (`visual-character-service.ts`): the per-view generate/validate/upload is now `generateCandidateView` (one view → `NewVisualAsset`) and set assembly is `assembleCandidateSet` (records the set from the per-view assets). `requestCandidateSets` (the direct, non-durable path used by `visual-characters.integration.test.ts`) is preserved and reuses the same private helpers. IDs stay DETERMINISTIC under a workflow: `candidateSetId = nameBasedUuid(workflowId, "set", setIndex)`, `assetId = nameBasedUuid(candidateSetId, "asset", view)`, seed + storage key derived from those — so a replayed view reproduces the same asset/key/bytes (`onConflictDoNothing` + same-key overwrite).

**M9 `generate-illustration`** (`src/application/workflows/generate-illustration-workflow.ts`) — the paint ladder split into per-phase stages. Stages now: `prepare` → `paint-initial` → `paint-repair` → `paint-escalation` → `finalise`.

- Each `paint-<phase>` stage does AT MOST one image gen + one vision review + the app-code review decision (reuses `decideImageReview` from `src/domain/image-job.ts` — never reimplemented), and persists its verdict/outcome as stage output (`PaintPhasePayload`, IDs/metadata only).
- **Short-circuit:** `paint-repair` is a NO-OP unless `paint-initial`'s outcome was `repair`; `paint-escalation` is a NO-OP unless `paint-repair`'s outcome was `escalate`. So an approval, a generation failure, or an already-exhausted ladder skip the remaining phases (each no-op just writes a `skipped` marker so the engine advances). Per `decideImageReview`, a blocking wrong-identity/count failure still advances the ladder (initial→repair→escalation→manual) — it is never approvable (rule 7) and lands `manual`, matching the existing 3-generation identity-failure test.
- `finalise` reads whichever phase approved (its stored `winningAssetId`/`request`/`verdict`/`model`) and does the ADR-007 delivery (approve the stored original; NO encode). No approval → last-run phase decides `manual-review` vs `failed`; text stays readable, quarantined original stays undeliverable (rule 9).
- **Reference bytes** are re-resolved from `objectStorage` in each painting phase (`resolveReferenceImages`) — they NEVER enter a persisted stage-output payload. Deterministic ids (`nameBasedUuid(workflowId, "original"|"review", phase)`) keep each phase idempotent across replay.

**Cost safety net (per-workflow image-call ceiling, fails SAFELY / non-retryably if exceeded):**

- M4: `CANDIDATE_IMAGE_BUDGET.maximumImageCalls = REFERENCE_VIEWS.length` (6). Each `paint-<view>` stage, before generating, counts the OTHER already-completed view stage outputs (one per finished image call) and breaches via `imageCallBreach` if the ceiling is reached — a structural guard that trips only if the stage list were mis-extended.
- M9: `IMAGE_JOB_BUDGET.maximumImageCalls = IMAGE_PHASES.length` (3). Each paint phase rebuilds the ledger from the `image_generation_runs` rows already recorded for the workflow, EXCLUDING its own phase's rows (so an idempotent re-record on replay never falsely trips the cap), and breaches via `imageCallBreach` before spending.

**Tests updated (all on FAKE adapters, `STORYLIGHT_FORCE_FIXTURE_MODELS`, no paid calls):** the M4 workflow idempotency test (`src/db/workflow-engine.integration.test.ts`) now resets to `paint-${REFERENCE_VIEWS[0]}` and re-drives every per-view + assembly stage, proving the same single set (same id, six views) is reproduced. The M9 test (`src/db/chapter-illustration.integration.test.ts`) tightened the happy path to assert EXACTLY one generation (repair+escalation short-circuited) and added a **repair-path** test (initial non-blocking outfit failure → repair approves → escalation no-op = exactly 2 generations, publication approved). The identity-failure escalation-ladder test (3 generations → manual) is unchanged. 465 unit tests pass (was 464; +1 repair-path). `pnpm typecheck && lint && format:check && build && db:validate && db:check` all green.

Live on Vercel (personal account `rob-hs-projects`), production `https://storylight-two.vercel.app`, auto-deploying from `github.com/humet/storylight` `main`. Provisioned: **Neon Postgres** (marketplace → `DATABASE_URL`/`DATABASE_URL_UNPOOLED`; migrate with `DATABASE_URL=$DATABASE_URL_UNPOOLED pnpm db:migrate`), **Vercel Blob** private store `storylight-assets`, `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL`, and **`AI_GATEWAY_API_KEY`** (Rob created it in the dashboard; production + preview). Auto-promotion of `main` deploys to the production alias works — earlier manual `vercel alias set` was racing propagation, not a fix.

**WORKING in production (verified live):** sign-up → family bootstrap, character create/approve, **real AI story generation end-to-end** (Planning → Writing → Checking → published, genuine Claude prose in the reader), and **illustrations rendering** (a real PNG served through the authorized delivery route). Durable workflows run on Vercel Workflow (WDK).

**Key fixes to get here (all committed):**

- `withWorkflow()` in `next.config` — was missing, so workflows sat `queued`, never driven. This was THE reason generation hung.
- AI gateway credential passed **explicitly** via `createGateway({ apiKey: AI_GATEWAY_API_KEY ?? VERCEL_OIDC_TOKEN })` — the SDK's ambient OIDC auto-detection does not fire inside the WDK `"use step"` context. A stable `AI_GATEWAY_API_KEY` (present in every context) is what actually made model calls work; OIDC alone did not.
- **Child illustration jobs** now dispatched from the WDK step (`start(driveWorkflowRun, …)`); the step builds the runtime directly so `dispatcherRef` was null and child jobs were created-but-never-driven.
- **ADR-007: no image encoding in the serverless runtime.** `sharp` (native libvips) cannot be traced into Vercel/Turbopack function bundles (`ERR_DLOPEN` in every function — proven by an `/api/sharp-check` probe), and `@jsquash` WASM failed the same way (`fetch failed` loading its `.wasm`). Five tracing workarounds (serverExternalPackages, onlyBuiltDependencies, cross-arch, lazy-load, `node-linker=hoisted`, `outputFileTracingIncludes`) did not work; the last broke serverless packaging via pnpm symlinks. Resolution: the runtime does NO image encoding — deliver the approved ORIGINAL; the fake chapter model uses a tiny dependency-free PNG encoder (`src/adapters/images/png-encoder.ts`). Removed `sharp`, `@jsquash/*`, `.npmrc` hoisted linker, and the pnpm sharp allowlist. Responsive derivatives are deferred to Vercel Image Optimization (its own follow-up).
- e2e forces the deterministic fixture models via `STORYLIGHT_FORCE_FIXTURE_MODELS=1` (Playwright webServer env) so `pnpm test:e2e` never makes paid/real-model calls even though `.env.local` carries a key; Playwright per-test timeout raised to 120s.

## Real illustration models (2026-07-20)

**Real AI illustration generation is wired** behind the existing image ports; the deterministic fakes remain for CI/e2e. Three new adapters under `src/adapters/images/**` (the only place `ai`/`createGateway` may be imported) reach the Gemini image + vision models through the **AI Gateway's LANGUAGE API** (`generateText` + `gateway.languageModel(slug)` — the gateway rejects these models on `generateImage`), mirroring `gateway-language-model.ts` (explicit `createGateway({ apiKey: AI_GATEWAY_API_KEY ?? VERCEL_OIDC_TOKEN })`, APICallError availability classification, raw provider detail only in `internalDetail`):

- `gateway-chapter-image-model.ts` — chapter SCENES. Builds the provider prompt from the model-neutral `ImageSceneRequest` (scene/style/prohibitions/continuity/placements/repair) and conditions identity on approved **reference bytes** passed as `{ type: "image", image }` content parts; reads the raster from `result.files` (`.uint8Array` + `.mediaType`).
- `gateway-vision-model.ts` — multimodal review via `Output.object`; sends each expected child's reference bytes + the scene, REPORTS a `VisionVerdict` (`decideImageReview` still owns the decision; an unreported child → `matches:false`, never approvable — rule 7). Uses `google/gemini-2.5-flash`.
- `gateway-image-model.ts` — M4 character reference VIEWS (text→image per view from the `CharacterVisualDescriptor` + Art Bible; per-view stateless port, so cross-view conditioning is deferred to a port-widening follow-up).

**Port signature extension (the key design change):** `ChapterImageModel.generate` and `VisionModel.review` now take a third arg `referenceImages: ReferenceImage[]` (`src/domain/reference-image.ts` — `{ characterKey?, view, bytes, contentType }`). `ImageSceneRequest` stays model-neutral (assetIds only, still pure/snapshot-tested). The **workflow** (`generate-illustration-workflow.ts` `paint` stage — it alone holds `objectStorage` + `visualAssetRepository`) resolves each selected child reference `assetId` → `getAsset` storage key → `objectStorage.read` bytes ONCE up front and passes them to every ladder phase + the review; bytes never enter a workflow payload/Postgres. Fakes ignore the new arg (structural typing).

**Selection** (`src/adapters/images/index.ts`, mirrors `adapters/ai/index.ts`): `STORYLIGHT_FORCE_FIXTURE_MODELS` → fake (precedence); else `AI_GATEWAY_API_KEY || VERCEL_OIDC_TOKEN` → real; else fake. Verified: all 464 unit + 20 e2e pass on fakes, `pnpm build` green with no env.

**Slugs used:** generation `google/gemini-3-flash-image` (routine/repair) + `google/gemini-3-pro-image` (premium escalation + M4 references) — seeded route slugs, unchanged; vision review re-pointed from the routine image slug to **`google/gemini-2.5-flash`** (a review is a multimodal _text_ read, not image generation — `image-route-registry.ts` `resolveReview()` now carries a dedicated `REVIEW_ROUTE`). Image models may not report token usage — cost is the flat `route.costMinorUnitsPerImage`; `resolvedModelId` comes from `result.response.modelId`. NOTE: if a `gemini-3-*-image` slug errors live, fall back to the confirmed `google/gemini-2.5-flash-image` in the registry (couldn't verify live — no paid calls made here).

**Follow-ups:**

- Live paid verification of image quality/identity is the orchestrator's job (no real model calls were made here). Existing M4 references in the deployed DB are fake SVGs; once regenerated by the real M4 adapter they become raster, which is what the gateway conditions best on.
- Model routes carry only `local-fake` eval approvals — run `pnpm eval` against real providers before trusting output quality (`docs/production-readiness.md`).
- **Preview env** unset; **Neon** is a single DB shared across environments.
- Cold-run flake: `src/db/migrations.test.ts` can hit Vitest's 5s per-test timeout on a cold cache (PGlite spin-up); passes in isolation. Consider raising the integration `testTimeout`.
