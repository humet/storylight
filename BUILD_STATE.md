- 2026-07-18 (M5): **Workflow state-transition matrix (ADR-006 appendix delegated this to M5).** Events drive statuses via the pure `transitionWorkflowStatus(from, event)` (illegal moves throw a client-safe `WORKFLOW_LOCKED`), exhaustively tested for all (status × event) pairs:
  - `queued  --claim--> running`, `queued  --cancel--> cancelled`
  - `running --yield--> waiting` (stage done, more remain), `running --retry--> waiting` (retryable failure, parked with back-off), `running --complete--> completed`, `running --fail--> failed`, `running --cancel--> cancelled`
  - `waiting --claim--> running` (resume next stage), `waiting --cancel--> cancelled`
  - `failed  --resume--> queued` (re-queue a dead-letter); `completed`/`cancelled` are terminal with no outgoing edges.
    `waiting` is the durable resting point between stages AND after a scheduled retry; `failed` is a RESUMABLE dead-letter (resumable state preserved per background-jobs.md), reached only via `requeue`. `claim` also reclaims a `running` row whose lease has EXPIRED (visibility timeout).
- 2026-07-18 (M5): **Storylight owns workflow state in Postgres (ADR-002); the dispatcher is only durable compute.** `workflow_executions` (status enum, `UNIQUE(user_id, request_id, workflow_type)` idempotency, `entity_id`, `current_stage`, `attempt`, lease columns, `next_attempt_at`, safe `last_error` jsonb, `input` jsonb = IDs+metadata only) + `workflow_stage_outputs` (`UNIQUE(workflow_id, stage_key)` = the idempotency anchor, + nullable lineage columns for M6 model routes). Engine semantics: **claim (lease) → skip if the stage output already exists → run handler → persist output ATOMICALLY with the stage advance → retry-with-back-off or dead-letter on failure**. The claim is a guarded conditional `UPDATE ... RETURNING` (queued/waiting, or running-with-expired-lease); every write is guarded by `lease_owner` so a stolen lease can't double-advance. Canonical transitions are the two pure domain functions; the repo just writes the computed status. DB enum + unique constraints back the application checks (AGENTS.md).

- 2026-07-18 (M5 review checkpoint): adversarial review found four workflow/visual defects, fixed the same day (tests extended, no schema/migration change needed). (1) HIGH — the WDK driver used a CONSTANT lease owner `wdk:${id}` for every drive, defeating the `WHERE lease_owner = :token` guard (a stale drive could double-advance after a reclaim), and treated a claim-`locked` result as `done` so a WDK replay inside the 60s lease window stranded the run forever. Fix: `wdk-workflow.ts` now mints a UNIQUE token per drive attempt (`wdk:${id}:${randomUUID()}`, generated inside the durable step so a replay reuses it) and, on `locked`, durably `sleep`s ~one lease then RETRIES, exiting only on terminal status. Mirrored as a testable `runToCompletion({ onLocked: "wait", lockedBackoffMs })` option on the engine (default stays `"stop"` — the in-process holder is a live sibling, so it already had unique tokens and no strand). New engine/repo tests prove a stale wdk-token drive can't advance after a new-token reclaim, and a locked drive waits+reclaims rather than exits. (2) MEDIUM — `requestCandidateSets` minted random ids and committed BEFORE the engine's stage-output write, so a crash re-ran the handler and duplicated a (paid, in M6) quarantined set. Fix: new pure `nameBasedUuid` (`src/domain/name-uuid.ts`, SHA-256→UUID, unit-tested); the stage passes `idempotencyKey = ${workflowId}:${stageKey}` (via new `StageContext.stageKey`) so set/asset ids are deterministic, and `recordCandidateSet` is now `onConflictDoNothing` + re-read. StageContext now documents that ALL stage handlers must be idempotent (M6+ copies this). Test: re-running the stage after a lost output yields exactly one set. (3) LOW — concurrent approval of two different sets could 500 on the `UNIQUE(character_id, version)` race / sibling-reject deadlock; `approveCandidateSet` now catches `23505/40001/40P01` and rethrows a safe `INVALID_COMMAND` ("This candidate set is no longer available to approve"). Test: one wins, the loser gets the safe error, exactly one version minted. (4) LOW — superseded approved assets stayed streamable by id; on re-approval the transaction now transitions the previous version's assets `approved→retired` (via the pure `applyVisualAssetTransition`) AND delivery additionally constrains approved reads to the character's CURRENT `visual_profile_id` (defence in depth). Test: after re-approval the old asset ids 404, the current set streams.
- 2026-07-18 (M5 known debt, not yet fixed): (a) `WorkflowRepository.claim` ignores the persisted `next_attempt_at` back-off — a `waiting` row parked for retry is claimable immediately, so the back-off is honoured only by the driving loop's in-memory `sleep`; a DIFFERENT dispatcher (or a WDK replay) could re-drive before `next_attempt_at`. Should be added to the claim's `WHERE` (`next_attempt_at IS NULL OR next_attempt_at <= now`). (b) `cancel`/`requeue` re-encode the transition ADJACENCY as SQL guards (`status IN ('queued','waiting')`, `status = 'failed'`) instead of calling the pure `transitionWorkflowStatus` — a drift risk if the matrix changes. Should compute the target via the pure function and guard on the source set it derives.
